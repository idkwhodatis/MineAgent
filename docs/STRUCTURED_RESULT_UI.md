# Retained structured execution navigation (025)

The Factor Library's exact-version workbench lists owner-bound structured
execution identities. This is read-only discovery, not OpenEvolve factor search
or permission to launch a new execution. The server reports installed historical
schema capability separately; unavailable schemas never fall back to a legacy
seed or advertise creation.

From a saved factor version, open an exact structured execution and its other
same-run execution. Individual results require an explicit release. Comparison
withholds **all** result-derived values, counts and change flags until both exact
releases have committed to the existing exposure ledger. GET does not silently
release. The release includes retained factor and market dataset extent; forward
labels remain exposure provenance, not trading inputs.

The released view separates actual snapshot reads, eligibility, scores, target
allocations, and observed native orders/fills. Native process IDs alone do not
constitute an economic change. Factor and parent-version links use actual lineage;
the initial lookback-2/lookback-1 fixture has independent root versions, not an
inferred parent-child evolution. Snapshot links use the verified **source RD run**,
not the structured execution's run ID. This is a maintained close-return fixture
and closed program, not arbitrary generated strategy support or a claim of gains.

## Acceptance boundary

Portable rendering/identity tests, generated API compatibility and local build
checks do not prove runtime execution. The required existing structured-factor
workflow invokes exactly one genuine Chromium case on the first existing
10-unit pair after retained storage relocation. It navigates from Factor Library,
proves one-sided release remains insufficient, explicitly releases both sides,
reads actual decisions/orders/fills, follows the source snapshot link, reloads,
returns through history, and rejects another owner. No routes are mocked and no
additional runtime units are created. The second existing 10-unit case retains
its real database/storage cold-restore and release-replay checks.

At implementation freeze, genuine Docker/PostgreSQL/Chromium acceptance remains
pending hosted execution; collection alone is not acceptance. The existing real Caddy gate also exercises these new routes through its runtime
mount with unavailable/missing-owner results, reload and Back. That gate is still
pending hosted execution and does not claim saved released-result coverage under
SUBPATH; portable prefix/fragment checks cover the released presentation links.
