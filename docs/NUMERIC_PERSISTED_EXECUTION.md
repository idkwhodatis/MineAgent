# Persisted numeric execution successor

This successor implements execution rather than another detached contract:

1. Resolve retained maintained source through the actual RD source graph.
2. Open the real evaluation ticket; commit exact prefix/cutoff and numeric
   admission together, with `logical_operation_id` equal to that cutoff ID.
3. Commit a one-shot launch claim before minting the private in-process token.
4. Durably write the launch journal and bounded immutable input files before
   Docker creation; attach before start, and observe the real private-namespace
   PID1, boot identity, image, container ID and original absolute deadline.
5. Read only protected MANU2 output, require complete EOF/no trailing frames,
   observe deadline exit, retain bounded opaque output, then positively remove
   the exact container and confirm the original kernel identity disappeared.
6. Re-resolve those actual persisted receipts to publish native HDF through
   revision019's real storage service. Atomically bind its unique normalizer
   consumer to a new persisted no-IPC unit in `factor_numeric`, reread that
   claim under a fresh fence, and run the real isolated normalizer.

No HDF/Parquet parser or generated Python executes in the host process. Input and
output reads remain bounded; Docker CLI subprocesses inherit no database secrets,
Docker credentials/context, proxy or arbitrary environment. Launch/run/stop CLI
operations share the original monotonic deadline plus one-second observation
allowance, rather than receiving a fresh timeout for each command.

Stop records explicitly distinguish `deadline_bound_met` from overdue recovery.
A later containment-only recovery can persist a truthful stop but cannot make an
overdue extraction eligible for publication. A lost attempt lease can persist
identity/whole-unit stop only; it cannot import extraction, publish results,
settle budgets or relaunch the same claim. Missing launch/identity response remains
uncertain, rather than inventing a PID, ticket, non-submission or stopped unit.
Input cleanup is recoverable after a durable verified stop checkpoint.

## Deliberate activation boundary

`run_registered_numeric_unit` still rejects: no production runtime catalog,
new-engine dispatcher, API route or arbitrary generated-source launch is installed.
The explicit `numeric_fixture` worker accepts only repository-maintained ABI
source bytes re-read from durable RD source evidence. Image IDs supplied by its
hosted test builder are test inputs, not evidence of production acceptance.
The existing disabled authenticated `prepare_candidate_cutoff` path is unchanged.
The fixed market fixture is not provider-byte/PIT, controller IPC or financial
performance acceptance. Prefix object codecs and the actual full RD controller
remain separate work; no fake source UUID, cutoff row, v1 role or positive stop is
used to bridge them.

## Composed dependency and verification

Apply after numeric017 + its `ee25089` corrections, source018 (including actual
source/evaluation/cutoff rows), and native019 (`factor_numeric` + unique native
normalizer claim). Public v1 commitments, neutral issuer and historical migrations
remain unchanged. Generated schema artifacts were updated in the preceding fix.

The existing numeric workflow now adds two mandatory actual PostgreSQL+Docker
cases: maintained source → candidate → native publication/claim → normalizer, and
lease loss after real running identity with containment but no output import.
Every successful output must have an actual stop observation inside its original
deadline bound. The controller precursor remains explicitly unexecuted/admitted;
these tests do not fabricate whole-run success or full composed cold restore.
JUnit skips/failures/errors cannot count as acceptance; only sanitized outcome
summaries leave the disposable runner. Cleanup uses exact owned IDs, never a
label query as authority to remove containers.

Local structural/FD/legacy regressions and test collection are not substitutes for
those hosted runs. PostgreSQL and Docker are unavailable in the local executor;
no actual composed execution or restore pass is claimed here.

## Authenticated controller submission checks

The maintained numeric issuers accept an internal host-only
`authorize_submission(session, fence)` callback when invoked by the real RD
controller bridge. It must return an exact issued `ControllerPeer`; the numeric
boundary independently revalidates its live kernel/socket identity and persisted
controller binding. A no-op, boolean, deserialized record or forged peer is not a
launch grant. `None` remains solely the existing explicitly labelled maintained
component fixture path, not a newly opened production/default entrypoint.

Controller-backed calls recheck current attempt and peer after the durable
one-shot claim, after input staging immediately before create, and again before
start. Database callbacks run outside the process namespace flock; after
reacquiring that flock, the supervisor rechecks the exact durable launch/root and
staged input bytes. The original deadline is never extended. This is not a claim
that a peer cannot die in the instant after a successful check. Known-dead peers
cannot submit new units after the image-inspection/staging delay.

If a pre-start check fails, any exact already-created container is contained by
its verified ID without inventing a PID or positive stop. Inputs and uncertain
reservation obligations remain retained; no extraction or refund follows from a
rejected callback. Actual controller+numeric hosted acceptance remains required.
